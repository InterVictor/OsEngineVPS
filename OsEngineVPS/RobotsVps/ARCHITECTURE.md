# VPS UI architecture

- The main-menu `VPS` button opens `RobotsVpsUi`, the connection and remote-administration window. SSH/MCP settings belong here, along with server deployment, updates, robot-script transfer and remote module restart/compilation controls as those operations are implemented.
- The main-menu `Bot Station VPS` button opens `RobotsVpsWorkspaceUi`, a separate workspace containing only `RobotsVpsLiteClone`: a full visual copy of `RobotUiLite` with its original panels, columns, buttons and checkboxes. It does not instantiate the local engine. Its XAML is independent so VPS-specific changes do not affect `RobotUiLite`.
- Per-computer connection settings are stored in `Engine/RobotsVpsSettings.txt`; the eighth line stores the auto-connect checkbox. When enabled, the main window opens the VPS settings window hidden and establishes the configured SSH tunnel and MCP connection after startup. The window remains alive in the background so its session can serve the workspace.
- The VPS Lite clone reads the shared remote session and polls `bot_get_list` every five seconds. The API response must supply robot number, public/internal name, strategy type, first security, open and closed position counts, and on/emulator flags. The VPS currently returns the list and parameter values, but the latest read-only check found no `is_on` / `emulator_is_on` fields and no `bot_set_state` tool; update the remote MCP server before expecting the state checkboxes to synchronize.
- UI parity milestone (2026-09-23): the VPS Lite clone mirrors the Lite window's localized tab names, window resize/panel splitter behavior, interface lock controls, utility buttons, version strip, shared theme resources, and its own saved layout key (`botStationVpsUi`). VPS-only source hooks remain isolated. Positions, stop-limit/historical positions, active/historical orders, portfolio, prime log and server panes currently display explicit placeholders until corresponding remote data APIs are connected. These placeholders must never initialize or query the local trading engine.
- Remote parameter dialog uses the same `ParamTabPainter` as `StrategyParametersUi`, including the native WinForms grid, editors, label formatting, and type-specific rendering. MCP `bot_get_params` also sends `ParamGuiSettings.ParameterDesigns` so custom foreground, selection, and underline styles can be reproduced. Older VPS MCP builds omit this optional metadata and fall back to the shared default style; deploy the updated server build to receive per-robot custom design metadata.
- `bot_get_params` includes each parameter's `tab_name`, along with the ordered names from `ParamGuiSettings.CustomTabs`. FF143 assigns standard parameters to `Base`, `Base1`, `Base2`, `Regime switch`; `Spectrum` is a custom chart tab and is not part of `BotPanel.Parameters`. The VPS dialog groups standard parameters in first-seen order and adds custom tab placeholders after them. The custom tab's chart content is not serialized yet. An older VPS MCP build without `tab_name`/`custom_tabs` cannot reproduce the correct tabs until its server package is updated.
- Closing the VPS settings window hides it and keeps SSH/MCP connected. `MainWindow_Closing` explicitly disposes the connection while OsEngine exits. The Parameters action opens a VPS dialog using `bot_get_params`, `bot_set_params` and `bot_click_param_button`. It renders rows in a WPF `DataGrid`, matching the working Bots → Parameters view, and groups rows by `tab_name` when supplied by the API. **When adding tabs dynamically, set `TabControlSettings.SelectedIndex` to 0**: otherwise WPF can leave it at -1, so the API data exists but the dialog content stays invisible.
- The robot On/Off and Emulator checkboxes are refreshed from `bot_get_list`; clicks send the requested state to `bot_set_state`, which changes the remote `BotPanel` and returns the server state.
- Build and launch the Windows terminal from `bin/Debug` only. Obsolete `bin/VpsBuild*` folders are removed to avoid launching an older copy by mistake.
- MCP `terminal_open_mode` can open Tester, Tester Lite, Robots, Robots Lite, Data, Optimizer, and Converter windows from a running Windows `MainWindow`. `tester_start` and `optimizer_start` are separate operation commands. The headless Ubuntu process has no GUI window for `terminal_open_mode` to display.
- SSH tunnel (2026-09-26): in-process via SSH.NET (`SshTunnel.cs`), no external ssh.exe. Authenticates with an OpenSSH private key file and/or a password (both secrets and the MCP API key are stored DPAPI-encrypted in `Engine/RobotsVpsSettings.txt`). The server host key is pinned on first use in `Engine/RobotsVpsKnownHosts.txt`; a changed key refuses the connection. The tunnel checks itself every 5 s and reconnects after a drop (5–60 s back-off). `RemoteMcpClient` re-initializes its MCP session on HTTP 404 "Session not found" (server restarted) and raises `Reconnected` when the event stream is back. Provisioning/update/script deployment actions are still future work.
- Server deployment (2026-09-26): the Server section of `RobotsVpsUi` has "Deploy / repair server". `VpsProvisioner` logs in over SSH (`VpsSshCredentials`: registered key / key file / password), uploads by SFTP `VpsServer/osengine-setup.sh` (source `Provisioning/osengine-setup.sh`, copied by the build), the headless build package `VpsServer/osengine-headless-linux-x64.tgz` (from `D:f-researchheadless`, not in git) and a tar.gz of the local `Custom` folder — the package and Custom only when missing on the server — then runs the idempotent script and streams its output to the log. First login with the root password from a computer creates an ed25519 key on the server (`osengine-client-<computer>-<date>` in `~/.ssh/authorized_keys`), verifies it, stores the private key DPAPI-encrypted in the settings and forgets the password; a second computer connects the same way. The MCP API key is read from `/opt/osengine/mcp.key` over SSH.
- Several terminals per VPS (2026-09-26): a terminal is a systemd service with its own folder, MCP port and MCP key — `osengine` (/opt/osengine, 6500, "main") and `osengine-<name>` (/opt/osengine-<name>, 6501+). `VpsInstances` finds them from `/etc/systemd/system/osengine*.service` (ExecStart gives root, port, key file) and starts/stops/restarts/removes them over SSH (remove keeps the data in `/opt/osengine-removed`). `RobotsVpsUi` keeps one SSH tunnel with a forward per terminal (local port = Local port + (VPS port − 6500)) and one `RemoteMcpClient` per running terminal, re-syncing every 10 s; `VpsRemoteSession` holds them by name. The "Bot Station VPS" button opens the only terminal directly or asks which one (`RobotsVpsInstancePickerUi`); each `RobotsVpsWorkspaceUi` is bound to one terminal (`RobotsVpsLiteClone.InstanceName`, shown in the title). A new terminal is created by `VpsProvisioner.DeployAsync(name, port)` — the setup script copies the build, Custom and the robot description cache from the main terminal on the server.
- Maintenance (2026-09-26): "Update build" uploads `VpsServer/osengine-headless-linux-x64.tgz` once and runs `osengine-update.sh` per running terminal whose build differs (version = SHA-256 of the package in `app/.package-sha256`, first 8 chars in the Build column): new build unpacked beside the old one, switch, 60 s MCP health check, automatic rollback; 3 `app.prev-*` kept. "Upload robots..." copies *.cs into `data/Custom/Robots` of the selected terminal (replaced files kept in `Custom/Robots-backup`, their `BotsDescription.txt` line removed), restarts it and checks compilation with `wiki_robot_info` (compiler output from journalctl). "Clean logs" deletes the terminal's log files except today's and vacuums the journal to 7 days; the setup script also installs a 200 MB journal limit and a daily cleanup of OsEngine logs older than 30 days. "Reboot VPS" runs `systemctl reboot` in the background; the tunnel reconnects by itself.
- Monitoring and backups (2026-09-26): every 10 s (with the terminal sync) `VpsMonitor` reads /proc/stat, /proc/meminfo, df, loadavg, uptime and each service's CPUUsageNSec over SSH — works even when OsEngine hangs. The Monitoring section shows CPU/RAM/disk for the last hour (`VpsSparkline`), per-terminal CPU in the terminals list, and raises alerts in the emergency alert window (`VpsAlarm` with hysteresis: CPU > 90 % for 1 min, RAM > 85 %, disk > 90 %). "Backup data" packs `data` (without logs) + `mcp.key` of the selected terminal and downloads it to `VpsBackups<host><terminal>` (14 kept; "Daily backup" does it once a day while connected; the folder is git-ignored). "Restore..." checks the archive, stops the terminal, keeps the current data as `data.before-restore-<time>`, unpacks, starts it (rolls back on failure) and reconnects with the key now on the VPS.
- Computers with access (2026-09-26): "Computers..." in the Server section opens `RobotsVpsComputersUi` — the keys of `~/.ssh/authorized_keys` on the VPS (`VpsComputers`: comment, type, SHA256 fingerprint via ssh-keygen). Keys this computer logs in with (registered key, key file; fingerprint computed locally from the key) are marked and cannot be revoked from here; "Revoke" removes a key by fingerprint and keeps `authorized_keys.bak-<time>`. The server build package is produced by `D:f-researchheadlessuild-package.sh` (refs, PathFix, ShimGen, publish) straight into `bin/Debug/VpsServer`.
- Trading actions without stubs (2026-09-26): portfolio "Close" (server_instance_close_position_on_board -> ServerMaster.ClearPositionOnBoard, same OsTraderMaster chain as the local button: cancels robots' orders, deletes their positions in that security, closes the rest at market), Stop Limit menu (bot_stop_limit_cancel, by opener number or all), "Add to position" (RobotsVpsPositionAddingUi = PositionAddingUi2 XAML + bot_position_add), robot risk manager (RobotsVpsRiskManagerUi = RiskManagerUi XAML + bot_risk_manager_get/set via BotPanel.PanelRiskManager). On a headless server risk-manager ShowDialog warnings are forwarded as emergency alerts (AlertMessageManager.TextBoxFromStaThread == null). New server_instance_* tools must also be added to the explicit routing list in McpMaster.
- File manager (2026-09-27): "Files..." (was "Upload robots...") opens `RobotsVpsFilesUi` over `VpsFileService` (SFTP for list/upload/download, SSH commands for copy/move/rename/trash + chown osengine). Only the data folders of the terminals, `/opt/osengine-trash` and `/opt/osengine-removed` are reachable, shown as places ("main: robots", "main: logs", ...). Delete moves to the trash (final delete only inside the trash). In a robots folder a replaced .cs is kept in Custom/Robots-backup and its BotsDescription.txt line is dropped; After every action that touches Custom/Robots (subfolders included, Dlls/BaseClasses excluded from the compile check) the terminal is told to re-read the scripts — wiki_robots_reload_scripts (BotFactory.ResetScriptCaches clears the script list and compiled-type caches; running robots keep their version) — and the added/replaced scripts are checked with wiki_robot_info. No button and never an automatic restart: if the terminal cannot re-read, the log says to use Restart.
- Emergency alert forwarding (2026-09-24): `AlertMessageManager.ThrowAlert` raises a local event which the MCP host publishes as `alert.raised` over the existing Streamable HTTP/SSE session. The Robots.VPS connection window receives it and inserts the remote bot/message/time into the same global emergency alert window using `ThrowRemoteAlert` (which deliberately does not re-publish, preventing an event loop). In headless mode, alert generation still publishes over MCP and skips local WPF rendering when no dispatcher text box exists. Watched compare-position mismatches call the same central alert manager after the module's verification delay, in addition to the existing error log. This changes the VPS/server sources `Alerts/AlertMessageManager.cs`, `MCP/McpMaster.cs`, and `Market/Servers/ComparePositionsModule.cs`; deploy the rebuilt server package as well as the Debug client for end-to-end delivery.

## 2026-09-27 — MCP access for AI agents

`McpJsonConfig` writes every VPS terminal into `<folder>/.mcp.json` of each folder from the "MCP access..." window (RobotsVpsMcpAccessUi; folders `;`-separated in settings line 13): `osengine-server` for the main terminal, `osengine-server-<name>` for the others, url = local end of the SSH tunnel, `X-Api-Key` = the terminal key. Runs on every terminal sync (connect + 10 s); writes only on change; removes entries of terminals deleted on the VPS, keeps stopped ones; other entries of the file are untouched. Claude Code (and other MCP clients) read the file when a session starts. Remove takes only the osengine-server* entries out.

## 2026-10-02 — update of the server build from a signed GitHub release (phone app)

- **Pipeline:** `headless/build-package.sh` builds the package on the PC -> `tools/publish-server-package.sh` signs it (ed25519,
  `ssh-keygen -Y sign`, key `~/.ssh/osengine_release_sign` stays on this PC) and publishes release `server-<sha256[:8]>` of
  InterVictor/OsEngineVPS with the package and its `.sig` -> `osengine-release apply` on the VPS (started from the phone app, or
  by hand) downloads it, verifies checksum and signature against `/etc/osengine/allowed_signers` (public half =
  `Provisioning/release-signers`) and updates every terminal one by one with `osengine-update.sh` (health check, automatic
  rollback; the first failure stops the run). The run is a transient systemd unit, so it survives a lost SSH session.
- **VPS files:** `/usr/local/bin/osengine-release` (`Provisioning/osengine-release.sh`: `check` / `apply [--only svc]` / `status`),
  `/usr/local/lib/osengine/osengine-update.sh`, `/etc/osengine/{release.conf,allowed_signers}`, state in `/var/lib/osengine-release`.
  `VpsProvisioner.InstallReleaseToolAsync` installs / refreshes them on every "Deploy / repair" and "Update build".
- **Why signed:** the VPS trades with real keys; with the signature a stolen GitHub account cannot ship code to it.
- **Publishing does not restart anything.** Terminals restart only when the update is applied (phone / `osengine-release apply`);
  the phone shows the open positions first and asks for the screen lock.

**2026-10-02 (later): the public release was taken down.** The OsEngine license (`LICENSE`, 3.2 and 3.3) allows modified code and derived
software for personal / internal use only, so the package (a build of modified OsEngine) must not sit in a PUBLIC repository without the
right holder's permission. `tools/publish-server-package.sh` now refuses to publish while the repository is public. Until the permission is
there or the repository is private, the phone update shows "no signed server release found"; terminals are updated from the PC
("Update build" in OsEngineVPS). A private repository would need a read-only token on the VPS for the download.
